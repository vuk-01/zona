# Decisions

Why this repo does things the way it does. Each entry is an ADR (architecture decision record):
context, the decision, and what it costs or buys. Rules in `.claude/rules/` and the reviewer agents
cite these numbers, so the rule and the reason stay linked. Add a new ADR when you make a choice the
team would otherwise re-discuss; never renumber an old one, mark it "superseded by ADR-0XX" instead.

### ADR-001 · The backend is its own repository; the contract travels with every change
**Superseded by ADR-018.**
**Context:** a feature almost always touches the backend, the frontend and `docs/entities.md` in between, but the two sides live in separate repositories.
**Decision:** this repository holds only the backend; `docs/entities.md` is the shared contract and a copy of it lives in the frontend repo. A change to the contract is made in both repositories in the same round of pull requests, and the backend PR names the frontend change it requires.
**Consequence:** nothing is "merged on one side only" by accident: `contract-keeper` reports "Contract changed: yes" and the frontend repo gets the same edit before the feature is called done.

### ADR-002 · `docs/entities.md` is the contract
**Context:** frontend and backend are built in different workshops, in different repositories, sometimes by different people.
**Decision:** fields, types, routes, status codes, error codes and the error shape are agreed in `docs/entities.md` before code; code and doc change in the same commit.
**Consequence:** code is the source of truth for what the system *does*, the doc for what was *agreed*; `contract-keeper` reports where they differ.

### ADR-003 · SQLite by default, Postgres through `DATABASE_URL`
**Context:** students must run the API in minutes on any laptop; some teams deploy to Postgres.
**Decision:** `sqlite:///./data/app.db` is the default; `DATABASE_URL` switches to Postgres with no code change; `SessionFactory` picks the engine options per backend; migrations use `render_as_batch=True` so they run on both.
**Consequence:** every column type and constraint must work on both engines; no engine-specific SQL.

### ADR-004 · Schema changes are migrations; committed migrations are history
**Context:** a table that exists only on the agent's laptop breaks every teammate and CI.
**Decision:** no `Base.metadata.create_all` outside `tests/integration/conftest.py`; every model change gets an Alembic revision through `poetry run makemigrations "<what>"`; a revision that is committed is never edited (`guard-edits` enforces it), a new one is added instead.
**Consequence:** `poetry run alembic check` is part of "done"; autogenerate output is read and fixed before `poetry run migrate`.

### ADR-005 · One error shape: `{"detail", "code", "fieldErrors"?}`
**Context:** clients (the frontend repo) show errors next to fields, switch on a stable code, and need one predictable format; the author's production backends answer `{"detail", "code"}`.
**Decision:** services raise a domain exception from `app/<domain>/exceptions/` that extends one of `NotFoundException`, `InvalidRequestException`, `UnauthenticatedException`, `ForbiddenException`, `ConflictException`, `ServerException` (`app/utils/exceptions.py`) with a human `message` and a snake_case `code`; the handlers in `app/app.py` map the base class to the status and answer `{"detail": message, "code": code}`, plus `"fieldErrors"` when a field is at fault; Pydantic's `422` is rewritten to the same shape with `code: "validation_error"`. No bare `HTTPException`, no status codes in services, no swallowed exceptions.
**Consequence:** clients (the frontend repo's `ApiError`) read `message` (from `detail`), `code` and `fieldErrors`; tests assert on the body, not just the status.
**Amended (spaces):** a seventh base class, `UnprocessableEntityException` → `422`, for input that is well-formed but breaks a rule only the service can check (a `PATCH` that leaves a space invalid as a whole; later `invalid_slot`, `booking_in_past`, `invalid_status_change`). `InvalidRequestException` stays `400` and is not used for contract `422`s.

### ADR-006 · The owner comes from the token, never from the body
**Context:** `ownerId` in a request body lets any signed-in user create or claim records as someone else.
**Decision:** write endpoints depend on `get_current_user` (`CurrentUser`); the service sets `owner_id=current_user.id`; request schemas have no `id` or `ownerId`; ownership is checked in the service and raises the domain's `Not...OwnerException` (`403`).
**Consequence:** IDOR is a review item for `security-reviewer`; tests include a `403` for every owned record.

### ADR-007 · Invariants are database constraints, not `if` statements
**Refined by ADR-019, ADR-023.**
**Context:** "one email per user" checked with a `SELECT` then `INSERT` fails under two concurrent requests, and does not hold for rows written by a script.
**Decision:** `unique=True`, `CheckConstraint`, `nullable` and `ForeignKey(ondelete=...)` carry the rules; Pydantic validates input for a good message, the database guarantees the data; the service turns `IntegrityError` into a `ConflictException` subclass (`409` with `fieldErrors`).
**Consequence:** every constraint is a migration, and the same limits appear in `schemas/`, the `StrEnum` in `models/` and `docs/entities.md`.

### ADR-008 · Timestamps are `TIMESTAMP(timezone=True)` with `server_default=func.now()`
**Refined by ADR-022.**
**Context:** naive datetimes take the server's local timezone, which differs between laptops, CI and a server; a Python-side default is skipped by anything that writes rows without the ORM.
**Decision:** every timestamp column is `TIMESTAMP(timezone=True)` (`sqlalchemy.DateTime` is banned by ruff) with `server_default=func.now()`; `UtcDatetime` in `app/utils/schemas.py` serializes as `...Z` whatever the engine returned.
**Consequence:** clients (the frontend repo) receive one format; `DateTime`, `datetime.now()` and `datetime.utcnow()` are review findings.

### ADR-009 · SQLAlchemy 2 typed style, one transaction per endpoint, synchronous `def`
**Context:** `async def` endpoints with a sync session block the event loop and hide the bug until load; commits scattered through services make rollback on error impossible.
**Decision:** `Mapped[]` + `mapped_column`, `select()` queries; every endpoint is registered on a `DBAPIRouter`, whose `db_session_handler` opens the thread-scoped session, commits when the endpoint returns and rolls back when it raises; repositories call `flush()` and never `commit()`; route functions are plain `def` (FastAPI runs them in a thread pool).
**Consequence:** no `async def` in `api/` or `services/` unless the code awaits something that is truly async; no `Column()`, no `session.query()`, no `commit()` outside `app/database/`.

### ADR-010 · camelCase JSON through `CamelCaseModel`; endpoints return schemas, not models
**Context:** Python is snake_case, TypeScript is camelCase; converting by hand drifts; a model returned from an endpoint lazy-loads after the session is closed.
**Decision:** every request schema extends `CamelCaseModel`, every response schema `CamelCaseResponseModel` (`alias_generator=camelize` from pyhumps, `populate_by_name`, `from_attributes`); services build `...ResponseSchema.model_validate(model)` and the endpoint's return annotation is that schema (FastAPI derives `response_model` from it).
**Consequence:** `imageUrl` in JSON is `image_url` in Python; a schema that does not extend one of the two bases, or an endpoint annotated with a model, is a bug.

### ADR-011 · Tests are part of the endpoint, in two layers
**Context:** an endpoint that "works in the browser" is not verified for the cases that matter: no token, wrong user, unknown id, bad input; a suite that needs a database for every assertion is slow and hides which layer broke.
**Decision:** `tests/unit/test_<name>_api.py` tests the HTTP layer with the service replaced by `create_autospec(I...Service)` in the DI container (routing, validation, auth, error shape, what reached the service); `tests/integration/test_<name>.py` runs the whole stack against a temporary SQLite database through the API with the fixtures `auth_headers`, `other_auth_headers`, `<entity>_id`; every route has the happy path plus `401`, `403`, `404`, `422` with `fieldErrors` where they apply.
**Consequence:** `verify-changes` runs the suite when the agent stops; a new endpoint without tests is BLOCKED in `/review-changes`.

### ADR-012 · No SQL strings
**Context:** f-strings and `.format()` in SQL are injection; `text()` bypasses the typed models.
**Decision:** queries are built with `select()`, `update()`, `delete()` on the models inside repositories; filters are column expressions; `ilike(f"%{search}%")` is a parameter, not SQL.
**Consequence:** `text(` and `f"SELECT` are review findings; a query that cannot be expressed with the ORM is a design question, not a `text()`.

### ADR-013 · Poetry manages Python, `manage.py` is the command line, dependencies need approval
**Context:** mixed `pip`/`venv`/`uv` setups produce "works on my machine"; an unreviewed dependency is a supply-chain and licensing risk; the author's production backends use Poetry and a `manage.py` with `poetry run <command>` shortcuts, so the starter should feel the same.
**Decision:** Poetry only (`poetry install`, `poetry run`, `poetry add`), virtualenv in-project; `manage.py` defines the commands and `pyproject.toml` exposes them as `poetry run start | test | lint | typecheck | makemigrations | migrate | seed`; `poetry.lock` is generated, never edited; the agent proposes a dependency with name, reason and alternative and the user runs `poetry add` (`guard-bash` enforces it).
**Consequence:** `pyproject.toml` + `poetry.lock` are the single source of the environment; `pip install` and `uv` never appear in docs or commands; a new command is a `BaseCommand` subclass in `manage.py`, not an ad-hoc script.

### ADR-014 · Domain packages with `api/`, `models/`, `repositories/`, `schemas/`, `services/`, `exceptions/`; thin endpoints
**Refined by ADR-020.**
**Context:** a global `routers/`, `models/`, `schemas/` split spreads one entity over distant folders; logic in endpoints cannot be tested or reused; the author's production backends group everything about one domain under `app/<domain>/` with one subfolder per role, and that is the layout students will meet at work.
**Decision:** `app/<domain>/{api,models,repositories,schemas,services,exceptions}/<entity>.py` plus `routes.py`; no `__init__.py` below `app/` (namespace packages; mypy runs with `explicit_package_bases`, `load_all_models()` walks `app/*/models/`); an endpoint parses input, calls one service method and returns; rules and ownership live in the service, the session and the queries in the repository; shared code lives in `app/database/`, `app/utils/`, `app/config/`, `app/deps.py`; dependency direction is `utils/database/config -> domains -> app.routes -> app.app`, and domains import each other only through models under `TYPE_CHECKING` or through another domain's Protocols.
**Consequence:** a new entity is one folder plus one migration, two test files and one section in `docs/entities.md` (`/new-entity`); a `__init__.py` under `app/<domain>/` is a review finding.

### ADR-015 · Dependency injection with kink: a Protocol per service and repository
**Context:** services that build their own repositories (and repositories that build their own engine) cannot be replaced in a test, so every test needs a database; FastAPI's `Depends` alone wires HTTP, not the layers below it.
**Decision:** every service and repository declares a `Protocol` (`IListingService`) and registers its implementation with `@inject(alias=IListingService)` from `app/utils/di.py`; constructors take Protocols and `ISessionFactory` and are resolved by the container; endpoints get a service with `Depends(get_di_entity(IListingService))`; `SessionFactory` and `Settings` are singletons; tests override with `add_to_di_container(IFoo, mock)` and restore with `remove_from_di_container(IFoo)`.
**Consequence:** a service or repository must be imported somewhere reachable from `app/routes.py` (the `api/` module imports it) so the decorator runs before the first request; a class without a Protocol and `@inject` is a review finding.

### ADR-016 · Lists are paginated with `Page[T]`
**Context:** a `GET` that returns every row works with 3 seeded records and times out with 30 000; adding pagination later changes the contract for every client.
**Decision:** list endpoints take `PaginationParams` (`?page=`, `?size=` capped at 500, from `get_pagination_params`), repositories return `Page[Model]` through `paginate()` in `app/utils/pagination.py`, services map it to `Page[...ResponseSchema]`, and the JSON is `{"total", "items", "pages"}`.
**Consequence:** clients (the frontend repo) read `items`; a list endpoint without `pagination_params` is a review finding.

### ADR-017 · Strict typing: mypy strict, ruff's full rule set, black, `from __future__ import annotations`
**Context:** an untyped backend lets the agent return a model where a schema was expected, pass a string where an enum was agreed, or forget a `-> None`; the author's production backends run the same strict configuration, so a project that passes here passes there.
**Decision:** `pyproject.toml` enables mypy strict options (`disallow_untyped_defs`, `warn_return_any`, pydantic plugin, ...) for `app/` and `tests/`, the ruff rule groups from production (E, F, B, I, UP, RUF, TID, FAST, TRY, DTZ, PT, SIM, ARG, N, ...), black at 100 columns, and `from __future__ import annotations` as a required import in every file; `poetry run lint` and `poetry run typecheck` must pass before "done", and `verify-changes` runs them when the agent stops.
**Consequence:** `sqlalchemy.DateTime` and `kink.inject` are banned imports (use `TIMESTAMP` and `app.utils.di.inject`); a `# type: ignore` needs a code and a reason.

### ADR-018 · One monorepo; the contract has two identical copies
**Context:** the backend started as its own repository (ADR-001) and now lives in this monorepo next to `frontend/`, so one pull request can change the backend, the frontend and the contract together.
**Decision:** the contract is `docs/entities.md` at the repo root, with an identical copy at `backend/docs/entities.md` (the one `backend/CLAUDE.md` loads); both copies change in the same commit and stay identical. A contract change updates the frontend under `frontend/src/` (`features/<name>/api/<name>-api.ts`, `types.ts`, the forms in `features/<name>/components/`) in the same pull request, or adds what is left to `docs/follow-ups.md` and names that follow-up in the pull request description.
**Consequence:** `contract-keeper` edits both copies, confirms they are identical and ends with "Contract changed: yes/no"; two copies that differ, or a contract change with neither the frontend change nor a follow-up, is a review finding. A feature is done only when the frontend has caught up, follow-up included.

### ADR-019 · Which `IntegrityError` is caught, and what it answers
**Refined by ADR-021.**
**Context:** ADR-007 makes the database the guarantee and says the service turns `IntegrityError` into a `409`. In practice that became a catch-all `409` "please try again" (`user_conflict`, `space_conflict`) for refusals that could not happen, or were not a conflict: a `NOT NULL` that Pydantic let through (a `500` on listings), or a foreign key to a user deleted during the request.
**Decision:** every `CHECK` and `NOT NULL` has a Pydantic twin, so the database does not refuse valid input for them. `IntegrityError` is caught only for a rule the input cannot check, and the answer names the rule: a UNIQUE column → a `ConflictException` subclass, `409` with `fieldErrors`; a foreign key to the signed-in user on `POST` → `401 invalid_token`; a foreign key to another row named in the request → that entity's `404`. For a foreign key the repository inserts inside a SAVEPOINT and the service checks, through the other domain's Protocol, whether the referenced row exists; when it does, the error is re-raised. A row deleted while its `PATCH` or `DELETE` runs answers `404` (`StaleDataError` from `save()`, or no row from `DELETE … RETURNING id`).
**Consequence:** no `<entity>_conflict` code without a UNIQUE behind it; a new foreign key on `POST` comes with an integration test that deletes the referenced row over a second connection right before the INSERT; an `IntegrityError` that reaches the client as a `500` is a missing Pydantic twin and a review finding.

### ADR-020 · A repository may query another domain's table
**Context:** ADR-014 lets domains reach each other only through models under `TYPE_CHECKING` or through Protocols. Some queries need another domain's table in the same SQL: `GET /api/spaces?favoriteOf=` filters spaces by one user's favorites, sorts them by when they were saved, and paginates; through a Protocol that becomes two queries and a page that no longer matches the filter. The auth domain already reads and writes `users` with the `User` model.
**Decision:** a repository may import another domain's model at runtime to build a query (a JOIN, a filter, an ORDER BY), and still returns only its own domain's models. Everything else crosses domains as before: services, schemas and endpoints use another domain through its Protocols (`ISpaceService`, `IUserRepository`) and may raise its domain exceptions; models refer to each other by string name with `TYPE_CHECKING` imports, never at runtime. Existing cases: `app/auth/repositories/auth.py` queries `User`; `app/auth/services/auth.py` builds `User` rows, because auth owns account creation; `app/auth/schemas/auth.py` reuses the `UserMode` enum.
**Consequence:** a cross-domain JOIN lives in one repository and is covered by that domain's integration tests; a service that imports another domain's model or concrete repository (not its Protocol) is a review finding, except in auth.

### ADR-021 · Idempotent writes: a repeat is not an error
**Context:** ADR-019 answers a UNIQUE refusal with `409` and a row deleted while its `DELETE` runs with `404`. Some writes are idempotent in the contract, because the client may send them twice on purpose: saving a favorite is a double click on the heart, and removing it is safe to repeat.
**Decision:** when `docs/entities.md` makes a write idempotent, the repeat is not an error. A `POST` whose UNIQUE pair already exists answers `200` with the existing row unchanged, not `409`; the INSERT still runs first in a SAVEPOINT and the existing row is read after the refusal (no SELECT before it, ADR-007). A `DELETE` answers `204` whether or not a row went, also when a parallel request removed it first, not `404`. Every other write keeps ADR-019.
**Consequence:** favorites is the first case (`POST /api/favorites`, `DELETE /api/favorites/{space_id}`); a new idempotent write is named as such in `docs/entities.md`, and its integration tests cover the repeat and the parallel case.

### ADR-022 · Booking times are local wall-clock hours in Europe/Podgorica
**Context:** a guest books "Tuesday 10:00–12:00" in the city of the space, and opening hours are local time too. ADR-008 covers moments the backend records (`created_at`), not times a person picks. A UTC timestamp for the start and the end would move the slot by an hour across a DST change and turn "whole hours inside the opening hours" into timezone math in every query.
**Decision:** a booking stores `date` (`DATE`) and `start_hour`, `end_hour` (`SMALLINT`, `end_hour = 24` is midnight) as wall-clock time in Europe/Podgorica; the JSON is `YYYY-MM-DD` and `HH:00`. One more column, `ends_at` (`TIMESTAMP(timezone=True)`, UTC), is computed in Python with `zoneinfo` when the booking is created, only so SQL can derive `finished` and `expired` (`ends_at <= now`); it is never returned. "Now" comes from `IClock`, never from `func.now()` or `datetime.now()`, so tests fix it with `FixedClock`; the local-time helpers (`LOCAL_TIMEZONE`, `local_hour_to_utc`, `hour_exists`) live next to it in `app/utils/clock.py`. A slot containing an hour that does not exist that day (2027-03-28 02:00, clocks go forward) is `422 invalid_slot`; an hour that exists twice (2026-10-25 02:00, clocks go back) is its first occurrence (`fold=0`). A start that is not strictly after now is `422 booking_in_past`.
**Consequence:** the overlap rule compares small integers on one date, with no timezone math in SQL; DST is tested with a fixed clock on both change dates; a datetime column for a slot, or `func.now()` in a booking query, is a review finding.

### ADR-023 · Capacity per hour is held by a lock on the space row
**Refined by ADR-024.**
**Context:** "at most `deskCount` (or 1) confirmed bookings in any hour of a space" is a rule across rows. ADR-007 wants rules as constraints, but no portable constraint counts rows per hour: `EXCLUDE` exists only on Postgres and cannot count desks. Read, count, then write without a lock lets two parallel confirms both see the last free desk and both take it.
**Decision:** a write that must keep such a rule serializes on the space row. The lock is the first statement of the transaction, then the read, the count and the write, which is a compare-and-set on the status (`UPDATE ... WHERE status = :expected RETURNING id`). `ISpaceRepository.lock_for_booking(booking_id)` finds the space through a subquery on `bookings`, so nothing is read before the lock; `ISpaceRepository.lock(space_id)` does the same for `DELETE` and `PATCH /api/spaces` (bookings PR 2). The lock is one statement on both engines (ADR-003), a no-op `UPDATE spaces SET id = id WHERE id = (...) RETURNING id`: on Postgres a row lock, on SQLite the database's write lock (RESERVED); the next writer waits for it, on SQLite through the driver's busy timeout. Writes that take no room (cancel, decline, delete) use the compare-and-set without the lock; `POST` counts too, but only as advice, because a `pending` booking takes no room.
**SQLite relies on pysqlite's legacy transaction mode.** Python's `sqlite3` driver, with the default `isolation_level=""` (`autocommit=LEGACY_TRANSACTION_CONTROL`), sends `BEGIN` only right before the first `INSERT`, `UPDATE` or `DELETE`. The `SELECT`s before the lock (`get_current_user`, ...) therefore run outside a transaction, and the lock's `UPDATE` starts a fresh one. With `autocommit=False` (Python 3.12+) or SQLAlchemy's "emit `BEGIN` on connect" recipe, those `SELECT`s would open a read transaction, and a second writer could get `database is locked` (`SQLITE_BUSY`) instead of waiting. A change to the SQLite driver settings means checking this again; `tests/integration/test_bookings_concurrency.py` fails when it breaks.
**Consequence:** on Postgres the no-op `UPDATE` writes a new row version with the same values (a dead tuple for vacuum). A rule across rows without a lock as the first statement, or a read before the lock, is a review finding. The concurrency tests prove that the second writer waits in the database (`[200, 409]`), and a control test without the lock must overbook.

### ADR-024 · Who may confirm is checked before the lock
**Context:** ADR-023 makes the space lock the first statement of a confirm. Any signed-in user could then send `PATCH {status: confirmed}` for someone else's booking, and any guest for their own, and hold the lock until the request ended in `403`: on Postgres the space row, on SQLite the write lock of the whole database. The answer was right, but the lock was a free way to slow every writer down.
**Decision:** a confirm first reads who takes part, `IBookingRepository.get_participants(booking_id)` (`guest_id` and the space's `host_id`, as columns), and answers `404 booking_not_found`, `403 not_booking_participant` (neither the guest nor the host) or `403 not_booking_host` (the guest) without the lock: only the host may confirm. The lock follows, then everything ADR-023 reads after it. This read is safe before the lock because nothing it returns ever changes: `guest_id` and `space_id` are set on INSERT, `host_id` on the space's INSERT, and no `PATCH` takes them; a booking deleted after the check makes `lock_for_booking` return `None` (`404`). It selects columns, not the `Booking` entity, so nothing enters the identity map and the read after the lock still loads the row as the database has it then. On SQLite it runs outside a transaction like the `SELECT` in `get_current_user` (pysqlite's legacy mode, ADR-023), so it holds no lock.
**Ids are not forever on SQLite unless the table says so.** "Never changes" holds for a row, not for an id: without `AUTOINCREMENT`, SQLite gives a new row `max(id) + 1`, so when the last booking is deleted, the next one gets its id. Postgres sequences never repeat an id. Every step of a write names the booking by its id: the participant check, the lock, the read after it and the compare-and-set. Matching the row that was read (`_same_booking` in `app/bookings/repositories/booking.py`: `id`, `guest_id`, `space_id`) is not enough on its own. When the same guest deletes a booking and books the same space again, the new booking has the same `guest_id` and `space_id` as well as the id: the host's decline or the guest's delete changed it, and a confirm whose participant check ran before the delete locked the new booking, read it and confirmed it, a booking the host never saw. Confirm was therefore not covered by the match. So `bookings` has `sqlite_autoincrement=True` (`__table_args__` of the model, migration `1a1aed7865e4`, which rebuilds the table in batch mode; no table refers to `bookings`, so the rebuild cascades nowhere): SQLite then never hands out an id twice, as on Postgres, and a booking deleted after the participant check makes `lock_for_booking` return `None` (`404`) on both engines. `_same_booking` stays on every compare-and-set and the re-read after a miss, so a row that comes back under the same id some other way (an insert with an explicit id) still counts as gone (`404`). Autogenerate does not compare `sqlite_autoincrement`, so `alembic check` cannot see whether it is there; the table's SQL in `sqlite_master` shows `AUTOINCREMENT`.
**Consequence:** before a lock, a write may read only values that never change, and only as columns; the status, the count and anything else the rule depends on are read after it. A write after a read matches the row it read, never the id alone, and a table whose rows a request names by id and that can lose rows does not hand out an id twice (`sqlite_autoincrement`). `tests/integration/test_bookings_concurrency.py` proves that a confirm by someone else or by the guest answers `403` while another confirm holds the lock and never reaches it. In `tests/integration/test_bookings.py`, `test_a_new_booking_never_gets_the_id_of_the_deleted_last_booking` proves that ids do not repeat; `test_decline_or_delete_never_reaches_the_same_guests_new_booking_of_the_same_space` and `test_confirm_never_reaches_the_same_guests_new_booking_made_before_the_lock` prove what that protects (both fail without `sqlite_autoincrement`); `test_cancel_or_delete_never_reaches_a_new_booking_with_the_same_id` proves the match.

### ADR-027 · Fields computed from bookings: one query per page, in the bookings repository
**Context:** a space carries two fields that are not stored: `availableDesks` (desks free in the current hour) and, in the host's own list, `bookingCounts` (`{active, pending}`). Both count rows of `bookings`. Counted per space they cost one query for every space on the page (N+1), and two places would each decide which booking is `active`.
**Decision:** `IBookingRepository` counts for a whole page in one query each, grouped by space: `confirmed_at(space_ids, day, hour)` (confirmed bookings whose `[start, end)` covers the local hour) and `booking_counts(space_ids, now)` (`(active, pending)` per space). Both return a `dict` keyed by space id and leave out spaces with nothing to count. `booking_counts` uses `_returned_status(now)`, the same SQL as the bookings list's `status` filter, so "active" (`pending` or `confirmed` as returned, ADR-022) is written once. `SpaceService._to_responses` calls them once per page through the Protocol (ADR-020); `get`, `POST` and `PATCH` go through the same method with one space. Only desk spaces open at that hour go into `confirmed_at` (the others are `null` without a query), and `booking_counts` runs only for the host's own list. `availableDesks` is `max(deskCount − confirmed, 0)`: a `PATCH` may still lower `deskCount` below the confirmed bookings of the hour (`docs/follow-ups.md`). "Now" and the local hour come from `IClock` (ADR-022).
**Consequence:** a list stays at the same number of statements for 1 space and for many; `test_host_list_counts_bookings_in_the_same_queries_for_any_number_of_spaces` in `tests/integration/test_spaces.py` proves it with a different guest, different bookings and different counts for every space (`.claude/frequent-mistakes.md`), and fails with a query per space. `SpaceService` depends on `IBookingRepository` while `BookingService` depends on `ISpaceService`: no cycle, because neither depends on the other's service. A new field counted from bookings is one more grouped method here, never a query in a loop.
