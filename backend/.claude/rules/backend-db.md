# Backend database

- Models live in `app/<domain>/models/<name>.py` and use SQLAlchemy 2.0 style: `class X(Base)`, `Mapped[type]` annotations and `mapped_column(...)`; no `Column(...)` and no untyped attributes (ADR-009)
- `Base` comes from `app.database.base` and carries the naming convention, so every index and constraint has a predictable name that a later migration can drop
- Every table has `id: Mapped[int] = mapped_column(primary_key=True)` and `created_at: Mapped[datetime] = mapped_column(TIMESTAMP(timezone=True), server_default=func.now())`; `sqlalchemy.DateTime` is banned by ruff, use `TIMESTAMP` (ADR-008)
- Every foreign key sets `ondelete` (`CASCADE` or `SET NULL`) and `index=True`; relationships use string targets (`relationship("User", back_populates=...)`) and the other model is imported under `if TYPE_CHECKING:`, so models never import each other at runtime; a repository may import another domain's model for a query (a JOIN, a filter, an ORDER BY), services still go through that domain's Protocols (ADR-020)
- Allowed values are a `StrEnum` in the models module (`ListingCategory`, `BookingStatus`) and a `CheckConstraint` on the column, built from the enum so the two cannot drift (`_STATUS_LIST` in `app/bookings/models/booking.py`); schemas reuse the enum. Values derived on read and never stored (`finished`, `expired`) are a separate enum in the schemas module (`BookingReturnedStatus`), not in the CHECK
- What must hold for every row is enforced by the database: `unique=True`, `CheckConstraint`, `nullable`; Pydantic validates input, the constraint guarantees the data. Every `CHECK` and `NOT NULL` gets a Pydantic twin; the service catches `IntegrityError` only for a rule the input cannot check, and answers by the rule that refused: a UNIQUE column → a `ConflictException` subclass (`409` with `fieldErrors`), or `200` with the existing row when the contract makes the `POST` idempotent (ADR-021); a foreign key to the signed-in user on `POST` → `401 invalid_token`; a foreign key to another row named in the request (`spaceId` on a favorite or a booking) → that entity's `404`. For a foreign key the repository inserts inside `db.begin_nested()` and the service then checks whether the referenced row exists; if it does, the error is re-raised (a bug, `500`), never a catch-all `409` (ADR-007, ADR-019)
- A rule across rows that no constraint can hold (at most `deskCount` confirmed bookings in an hour) is kept under a lock on the parent row: the lock is the first statement of the transaction (`ISpaceRepository.lock_for_booking`, a no-op `UPDATE ... RETURNING id`, the same on SQLite and Postgres), then the read, the count (without the row being changed: `exclude_id`), and a compare-and-set write (`update(...).where(Model.id == id, Model.status == expected).returning(Model.id).execution_options(synchronize_session="fetch")`); never read-count-write without the lock, and never a read of what the rule depends on (the status, the count) before it. Before the lock a write may read only values that never change, as columns, not entities, so nothing stale sits in the identity map: confirm checks with `get_participants` that the user is the host and answers `403` (`not_booking_participant` or `not_booking_host`) without the lock (ADR-024). Only a write that takes room takes the lock (confirm); cancel, decline and delete use the compare-and-set alone. `"fetch"` is required on every compare-and-set `update()`/`delete()`: the default (`"auto"` → `"evaluate"`) sets the new value on the loaded object even when the database changed no row. A compare-and-set that changes no row reads again with `select()`, not `db.get`: no row → `404`, another status → `422` (ADR-023)
- Times a person picks in local time (a booking's `date`, `start_hour`, `end_hour`) are stored as local wall-clock values in Europe/Podgorica, not as timestamps; a derived UTC `TIMESTAMP(timezone=True)` (`ends_at`) is computed in Python with the helpers in `app/utils/clock.py`, and "now" comes from `IClock`, never `func.now()` in a query. In a query `now` is passed as `now.astimezone(UTC)`, because SQLite compares the stored value as text; read back, SQLite gives a naive datetime (UTC) and Postgres an aware one, so Python code adds `tzinfo=UTC` to a naive value before comparing (ADR-022)
- Repositories (`app/<domain>/repositories/<name>.py`) are the only place that touches the session: `db = self._session_factory()`, `select()` on the models, `add` flushes inside `db.begin_nested()`, `save` flushes after a change (a vanished row raises `StaleDataError` there, the service answers `404`), `delete` is `delete(Model).where(...).returning(Model.id)` and returns whether a row went, never `db.delete(model)` and never `db.commit()`; the endpoint's `DBAPIRouter` commits (ADR-009, ADR-015)
- Queries are built with `select()` on the models; never `text()`, f-strings or `.format()` with SQL, never `session.query()` (ADR-012)
- A list endpoint that reads a relationship on every row loads it with `selectinload` / `joinedload` in the same query; a query inside a loop is an N+1 (`/check-n1` finds them)
- Lists go through `paginate(query=..., pagination_params=..., db=db)` from `app.utils.pagination` and return `Page[Model]`; the service maps it to `Page[...ResponseSchema]` (ADR-016)
- Never call `Base.metadata.create_all` in app code; tables and columns come from migrations only (`tests/integration/conftest.py` may use it on its temporary database) (ADR-004)
- A model change is a migration: `poetry run makemigrations "<what changed>"`, then read the generated file in `alembic/versions/` and fix what autogenerate missed (renames, data moves, a `server_default` for a new `NOT NULL` column on a table with rows) before `poetry run migrate` (ADR-004)
- A new domain only needs a `models/` folder: `load_all_models()` imports every `app/*/models/*.py` for the app and for alembic, nothing is registered by hand
- Never edit a migration that has already been committed; add a new one (`guard-edits` blocks it) (ADR-004)
- Never run `alembic downgrade` on a database with real data without asking first (`guard-bash` blocks it)
- `poetry run alembic check` passes before a commit: no model change without a migration (ADR-004)
- Works on SQLite and Postgres alike: no engine-specific types or SQL; migrations use `render_as_batch=True` (ADR-003)
